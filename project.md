# Proxy Dock — Project Brief

**Status:** Concept / pre-implementation  
**Project directory:** `C:/projects/proxy-dock`  
**Stack:** Proposed — Tauri 2 + React/TypeScript + Rust/Axum + SQLite/SQLx (not yet approved)

## Product vision

Proxy Dock is a local AI-provider gateway and control plane. It brings multiple providers and their accounts together behind one stable endpoint, while keeping provider-specific adapters responsible for authentication, API differences, model discovery, and request/response translation.

The dashboard is where users manage providers, accounts, routing, model availability, health, and usage. External AI clients should usually need to configure only the unified gateway.

## Confirmed decisions

- Use a **hybrid architecture**: one unified gateway for normal client traffic plus provider-specific adapters behind it.
- Use one local application/process and one listening port for the unified gateway and all provider-specific endpoints. Provider endpoints are distinct URL paths on that same host and port; never assign a separate port per provider.
- The desktop app must support minimizing to the system tray/notification area and continuing to run the local gateway while minimized. Tray behavior, menu actions, and close-button behavior remain to be specified and implemented for the target OS(es).
- The unified gateway URL is the default integration point. Provider-specific endpoints are also first-class direct routes for their respective adapters, not separate servers.
- Namespace model IDs with the provider's stable slug **only on the unified gateway** to prevent collisions between providers. Provider-specific adapter endpoints retain normal, native provider model IDs without a provider prefix.
- Initial provider sections remain **ChatGPT, OpenCode, and Command Code Go**. Support distinct subscription/authentication flows beneath those providers: ChatGPT/Codex browser OAuth; OpenCode Go's separate subscription credential flow (the selected OpenCode subscription); and Command Code Go's CLI browser authorization. Never assume credentials from one flow are reusable in another or by Proxy Dock without an approved integration path. Command Code Go remains distinct from OpenCode Go and requires its special compatibility adapter: the existing `C:/projects/commandcode-go-proxy` bridges OpenAI/Anthropic-compatible client requests to Command Code's CLI-style `/alpha/generate` stream, rather than the documented Provider API. Treat the CLI-style route as a subscription-specific, potentially unstable integration; isolate it and verify the access contract/terms before release.
- Treat provider accounts as first-class objects: one provider can have multiple accounts, each with its own credentials, health, limits, and routing priority.
- Use a vertical, left-side, macOS Dock-inspired sidebar with large rounded-square tiles. Home is the top tile and is green; provider tiles follow beneath it.
- The supplied sketch is the visual reference for the sidebar's silhouette and tile arrangement, not a finished screen or a source of provider logos.

## Model IDs and gateway

Expose a provider-qualified model ID on the unified API, using this conceptual form:

```text
<provider-slug>/<native-model-id>
```

Examples:

```text
commandcode-go/z-ai/glm-5.3-flash
chatgpt/<native-model-id>
opencode/<native-model-id>
```

Use a stable machine-readable provider slug, not a display name. Preserve the native model ID exactly after the first provider-slug segment; native IDs may themselves contain `/`. The unified gateway resolves the provider prefix to the provider adapter and then routes to the selected account. This namespace is used only by the unified gateway; provider-specific adapter endpoints use the provider's normal native model IDs, without a Proxy Dock provider prefix. Aliases and routing policies may be added to the unified gateway without removing provider-qualified IDs.

Default client-facing endpoint (port/path to be finalized during implementation):

```text
http://127.0.0.1:<port>/v1
```

Expose the unified gateway and each provider adapter as distinct paths on the same local host and shared listening port—never as separate provider ports:

```text
http://127.0.0.1:<port>/v1                  unified gateway
http://127.0.0.1:<port>/commandcode/v1       Command Code adapter
http://127.0.0.1:<port>/opencode/v1          OpenCode adapter
http://127.0.0.1:<port>/chatgpt/v1           ChatGPT adapter
```

Each provider-specific path is a direct endpoint for that provider. It accepts and exposes the provider's normal native model IDs, without Proxy Dock's provider prefix. Only the unified `/v1` gateway uses `<provider-slug>/<native-model-id>`. All routes are served by the same local application and listener.

## Information architecture

### Home

A cross-provider overview with:

- Request and token usage, by provider, account, and model, with a selected time range
- Estimated cost by provider, account, and model where pricing data is available; distinguish estimates from provider-reported actuals
- Quota/limit tracking where a provider exposes it, including remaining quota, reset time, and usage period
- Active providers and account health
- Recent errors and rate-limit/quota events
- Recent routing, retry, and fallback activity

### Provider pages

Selecting a provider tile opens that provider's page. Show its status and accounts, with account-level health, request/token usage, cost, and quota/limit status. Include available models, authentication status, rate-limit state, quota remaining and reset time where available, default account, failover order, and provider-specific settings. Logs or recent events should help explain routing and errors.

### Accounts

An account belongs to a provider and is independently manageable. Track a user-assigned label, authentication state, health, supported models, request/token usage, cost, provider-reported quota/limits and reset times where available, and routing/failover priority. Clearly identify unavailable quota data and whether cost is estimated or provider-reported. Credentials must be stored securely and excluded from logs and diagnostics.

### Subscription authentication

Reference implementation: [`router-for-me/EasyCLIProxyAPI`](https://github.com/router-for-me/EasyCLIProxyAPI) is a Tauri/React/Rust desktop manager for CLIProxyAPI. Its OAuth authorization/account-management and credential/quota UI are useful architectural references, and its CLIProxyAPI core supports Codex OAuth. Treat it as an implementation reference, not proof that every provider uses OAuth or that its credential-handling approach is approved for Proxy Dock. Follow each provider's official flow and terms.

Use the provider's official subscription-based authentication flow rather than asking for API keys when subscription access is intended. Keep account tokens/credentials encrypted at rest; never log, expose, or send secrets to client applications. Keep provider auth modules separate and support sign-in, refresh, status, disconnect, and re-authentication.

- **ChatGPT/Codex:** target ChatGPT-account OAuth for Codex-compatible access. Official Codex local clients authenticate with a browser sign-in (`codex login` CLI or Continue to sign in in the desktop app), returning credentials to the client. Do not confuse this with ChatGPT web chat or assume arbitrary ChatGPT web session cookies authorize the gateway. Confirm an approved integration path for Proxy Dock before implementing token reuse.
- **OpenCode Go:** this is OpenCode's own subscription, not ChatGPT/OpenAI OAuth. Official docs say `/connect` → **OpenCode Go** → sign in at its auth page → copy and enter the issued API key. This is a subscription credential flow. Proxy Dock can either let users enter the issued key or launch/delegate setup through OpenCode; verify the provider's terms and supported programmatic use before forwarding requests.
- **Command Code Go:** use Command Code's own CLI login/browser authorization flow (`cmdc login` on native Windows; `cmd login` on macOS/Linux/WSL). The current compatibility bridge relies on Command Code CLI credentials and the CLI-style `/alpha/generate` interface. Encapsulate this private/proprietary route behind its adapter; do not assume it is a stable or officially supported public API. The user deferred integration testing until app building; verify then with an authorized account and review current official terms/permissions.

For Command Code Go, Proxy Dock can record its own request count and response token usage only when the upstream `totalUsage`/`usage` event provides it; the current bridge maps missing usage to zero and does not persist request history. Add persistence in Proxy Dock, but distinguish gateway-observed traffic/tokens from Command Code's authoritative billing totals. Treat Proxy Dock cost as an estimate unless reconciled with Studio: plan credits and model deals may not equal a simple public token-price calculation. The CLI `/usage` command shows the account's credit balance and live 5-hour/weekly meters; Command Code Studio's Usage page shows per-request cost and token counts. The official docs do not establish whether requests sent through the bridge's private `/alpha/generate` route appear in Studio's Usage page, so that needs a real-account test before claiming reconciliation. The bridge itself does not query Go-plan quota windows or account balances.

## High-level architecture

1. **Dashboard UI** — Home, provider/account management, usage, routing, logs, and settings.
2. **Control API** — Manages provider definitions, accounts, model metadata, routing policies, usage summaries, and health checks.
3. **Unified model gateway** — Serves external client requests, validates provider-qualified model IDs, selects an account, invokes the adapter, applies consistent retries/fallbacks where safe, and records usage/events.
4. **Provider adapters** — Encapsulate each provider's auth, API compatibility, model discovery, request/response mapping, streaming behavior, and provider-specific errors/limits.
5. **Persistence and secrets** — Stores configuration and usage data; protects credentials using an appropriate OS-backed or encrypted secret store selected for the chosen stack.

Keep the UI/control plane and model-traffic routes logically separated even if they ship in one process at first. Do not split adapters into separate processes unless a provider's isolation, dependency, or update needs justify it.

## Stack recommendation — proposed, not yet approved

Recommended stack: **Tauri 2 + React/TypeScript + Rust/Axum + SQLite/SQLx**. Use a single local application and shared listener for the dashboard/control API, unified `/v1`, and provider-specific `/<provider>/v1` paths. Store credentials in an OS-backed secret store; keep usage events, pricing snapshots, and quota observations in SQLite. The Rust adapter layer should keep provider-specific auth, API behavior, request/response mapping, and usage/quota capabilities isolated behind a shared interface. Command Code Go needs a dedicated integration path rather than being treated as a standard API provider. This is a recommendation only; confirm the Go API access flow and implementation feasibility before locking the stack.

No language, framework, database, or packaging approach has been approved yet. Decide the stack after comparing realistic options against these requirements:

- Reliable local installation and startup on the intended desktop OS(es)
- A responsive dashboard and maintainable provider/account UI
- Streaming proxy requests with low overhead and clear cancellation behavior
- Secure local credential storage
- Straightforward provider adapter development and testing
- Local persistence, migrations, backups, and useful diagnostics
- Packaging, updates, and a clean localhost-only security posture

Evaluate the UI, gateway, persistence, and desktop packaging together. Record the decision and trade-offs here before implementation; do not let an early prototype silently lock the product into a stack.

## Initial scope

The first usable release should integrate ChatGPT/Codex, OpenCode Go, and Command Code Go, with multiple accounts where supported; expose a unified provider-qualified model catalog and direct provider-specific endpoint paths on the same listener; and support account selection/routing, cost and request/token usage tracking by provider/account/model, plus provider-reported quota/reset information where available. Clearly label estimates and unavailable data. Use the official subscription flows: browser OAuth for ChatGPT/Codex and Command Code CLI login; OpenCode Go issues an API key after subscription authentication. Do not conflate OpenCode Go with ChatGPT/OpenAI OAuth or assume credentials can be shared. Use EasyCLIProxyAPI as a UI/architecture reference for OAuth account management and usage, not as proof that its flow supports these providers or that its implementation is automatically permissible. Reuse/refactor the adapter approach in `C:/projects/commandcode-go-proxy` for Go-plan routing: it translates compatible client requests to the CLI-style `/alpha/generate` event stream. Treat that upstream route as undocumented/private and potentially unstable; isolate it, avoid assuming the documented Provider API is available on Go, and verify compatibility and terms before release. Final API compatibility targets, authentication details, supported operating systems, and the shared gateway port remain to be confirmed during technical planning.

## Not in scope yet

- A fixed technology stack
- Mandatory separate processes or listening ports per provider
- Provider-prefixed model IDs on provider-specific adapter endpoints
- Inability to track cost, usage, and quota where data is available
- Final visual theme, exact tile palette, or a provider logo set
- Unverified claims about cost, quota, or model availability
